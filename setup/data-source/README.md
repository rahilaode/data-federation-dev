# Data sources

The two sources of the NPD case study (ADR-0027), each with its own schema monitor. The data is
the NPD benchmark (<https://github.com/ontop/npd-benchmark>), split by the Norwegian system that
owns it.

| Container | DBMS | Database | Host port | Tables |
|---|---|---|---|---|
| `datasources-pgsql` | PostgreSQL 15 (`debezium/postgres:15`, `wal_level=logical`) | `reporting` | 15433 | 25 tables, 184,275 rows: `wellbore_*`, `wlbPoint`, `strat_*`, `seis_*`, `sea*`, `field_production_*` |
| `datasources-mysql` | MySQL 8.0 (`quay.io/debezium/example-mysql:2.0`) | `registry` | 13306 | 45 tables, 72,996 rows: licences, fields, discoveries, companies, facilities, TUF, ... |

The init scripts run only when the data volume is empty, in this order:

| Script | PostgreSQL (`pgsql/`) | MySQL (`mysql/`) |
|---|---|---|
| `01-load-npd.sh` | Loads the whole NPD dump (`npd.psql`) | Loads the whole NPD dump (`npd.mysql`) |
| `02-split-*.sql` | Drops the 45 `registry` tables and the foreign keys that cross the sources | Drops the 25 `reporting` tables and the crossing foreign keys |
| `03-schema-monitor.sql` | Event trigger and `schema_monitor.*` tables, all 25 tables monitored | Event Scheduler job and monitor tables, all 45 tables monitored |
| `04-check-*.sh` | Fails the init unless there are 25 tables, 25 primary keys, 19 foreign keys, 25 monitored tables, 1 trigger | Fails the init unless there are 45 tables, 45 primary keys, 59 foreign keys (none dangling), 45 monitored tables, 1 event |

The dumps are mounted from `setup/npd/npd-benchmark/`, which `setup/npd/fetch-npd.sh` fills
(`start.sh` and `restart-ascam.sh` run it). `02-split-*.sql` is generated by
`setup/npd/tools/gen_split.py`. `./start.sh` removes the volumes and so reloads both databases;
the first load takes a few minutes, and `start.sh` waits over TCP until the checks have passed
(the temporary server of the init phase does not listen on TCP).

NPD names are mixed case (`wlbNpdidWellbore`). In PostgreSQL they must be double-quoted in SQL;
MySQL compares column names without case.

**Schema monitors.** `ALTER TABLE ... ADD COLUMN`, `DROP COLUMN`, and `RENAME COLUMN` are recorded
as rows of `ddl_event_log`. Debezium captures that log table only, never the business tables
(ADR-0017; C_safe in `docs/evaluation.md`). Whether a table is federated is decided by Knowledge,
not by the monitors.

- PostgreSQL: an event trigger on `ddl_command_end` writes every such statement on a table that is
  listed (and active) in `schema_monitor.captured_tables_ref` to `schema_monitor.ddl_event_log`
  (with `REPLICA IDENTITY FULL`); statements on any other table are not logged. The table name is
  taken from `pg_class` (so its case is kept) and the column name without its quotes.
- MySQL has no DDL triggers. The Event Scheduler runs `sp_detect_ddl_changes` every 10 seconds for
  the tables listed in `captured_tables_ref`; it compares `information_schema.COLUMNS` with the
  snapshot in `ddl_column_snapshot` and writes the differences to `ddl_event_capture`, from where a
  trigger forwards them to `ddl_event_log`. A column that disappears and a column that appears in
  the same table with the same position and type are recorded as one `RENAME COLUMN`. A change
  that is undone before the next scan is not seen (`docs/evaluation.md`).

Connect by hand:

```bash
docker exec -it datasources-pgsql psql -U postgres -d reporting
docker exec -it datasources-mysql mysql -umysql -pmysql registry
```
